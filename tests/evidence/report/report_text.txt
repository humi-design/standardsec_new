1.3 Overall Accessibility Status
This review confirms 23 Success Criteria failures out of the 56 assessed under WCAG 2.2 (a 41%
failure rate), against 22 passes and 11 not-applicable criteria. Several of the confirmed failures are
Level A issues that block core functionality outright — most critically, the entire primary navigation
menu (About Us, Login, Quick Links, KYC, Complaints) is unreachable by keyboard or mouse at
common viewport widths because the hamburger-menu toggle does not work, and the page’s own
“Skip to main content” link is permanently hidden from view even when it holds keyboard focus.
WCAG 2.2 Level AA conformance is not met in the site’s current state. Section 8 details every
confirmed issue with recommended fixes; Section 3 lists the narrower points that still need direct
confirmation before any associated result above is treated as final.
1.4 Key Findings (at a glance)
● Primary navigation is completely unreachable by keyboard or mouse at common viewport
widths — the hamburger-menu toggle is broken (a JavaScript bug), which cascades into
reflow, hover-content, and “multiple ways to navigate” failures as well (1.4.10, 1.4.13, 2.1.1,
2.4.5)
● The “Skip to main content” link is permanently clipped out of view via CSS, even while it
holds keyboard focus, so it can never actually be used (2.4.1)
● Every page on the site shares the exact same, non-descriptive title, giving users and screen-
reader software no way to distinguish one page from another (2.4.2)

● The Contact and “Create Account” forms have no programmatic or visible field labels and no
input validation of any kind (1.3.1, 2.4.6, 3.3.1, 3.3.2, 3.3.3)

3. Assessment Constraints
Unlike a review limited to static markup alone, this assessment included direct, hands-on browser-
based checks: computed colour-contrast ratios, computed focus styles, keyboard tab-order testing,
and viewport-width resizing to identify responsive breakpoints. A small number of narrower checks
were not carried to full completion, for the reasons below, and are flagged here rather than silently
folded into the results above:
● Full 200% text-resize content-loss check (1.4.4): pinch-zoom is confirmed not blocked at the
viewport level, but a complete pass checking for content loss or overlap at 200% zoom
across every page was not finished in this environment.
● True 320 CSS px reflow (1.4.10): the reflow failure identified was observed at an 894px
breakpoint (where the hamburger toggle breaks); a separate, dedicated check at exactly 320
CSS px was not performed.
● Form-submission behaviour (3.3.1, 3.3.3, 4.1.3): the contact form’s native required-field
validation was not triggered by an actual submission, to avoid tripping reCAPTCHA or
sending an unwanted message to the business; the related findings are based on markup
and attribute inspection rather than an observed submission attempt.
● Session and timing limits (2.2.1): no session timeout was observed on the public pages
reviewed, but this was not exhaustively tested across every page and state.
● No live screen-reader session (NVDA, JAWS, or VoiceOver) was part of this round of testing.
We recommend the residual items in Section 9 be confirmed before treating any associated result
above as final, particularly ahead of a formal compliance determination.

8.1 Broken Heading Hierarchy and Duplicate Heading Content
STATUS OPEN
WCAG 2.2 REFERENCE 1.3.1 Info and Relationships (Level A)
Heading order is broken across the site: H3 elements appear before the page’s H1, and
the hero carousel contains duplicate H1s. Separately, identical service content is
DESCRIPTION
marked up as an H5 in one section and as an H3 in a repeated section, so the same
content has two different heading levels depending on where it appears.
● Screen-reader users commonly navigate by heading level; a broken or
duplicated hierarchy makes the page's outline unreliable and disorienting.
IMPACT ON USERS ● Inconsistent heading levels for identical content suggest the underlying
template is duplicated or diverges between sections, risking further hidden
inconsistencies.
AFFECTED URL https://www.standardsec.com/index.html
● Establish a single, logical heading outline per page: one H1, followed by H2s
for major sections and H3+ for subsections, with no level skipped.
RECOMMENDATIONS
● Ensure the hero carousel renders one H1 regardless of which slide is active.

===== PAGE 13 =====
● Standardise the heading level used for repeated service-content blocks so the
same content is always marked up the same way.
POC
8.2 Contact Form Fields Have No Programmatic or Visible Labels
STATUS OPEN
1.3.1 Info and Relationships (Level A) / 2.4.6 Headings and Labels (Level AA) / 3.3.2
WCAG 2.2 REFERENCE
Labels or Instructions (Level A)
The contact form's Name, Email, and Message fields rely solely on placeholder text for
identification — none has a programmatic <label> element, and there are no visible
DESCRIPTION required-field indicators. Some headings elsewhere on the page are also non-
descriptive stat values (e.g. “#1”, “~30ms”, “0.0”) rather than text describing their topic
or purpose.
● Screen readers announce a field's purpose from its label; with placeholder-
only fields, users may hear no field name at all, or lose the prompt entirely
once they begin typing.
IMPACT ON USERS ● Sighted users with cognitive or attention difficulties lose the field's purpose as
soon as they start typing, since placeholder text disappears on input.
● Non-descriptive headings give screen-reader users navigating by heading no
indication of what a section contains.
AFFECTED URL https://www.standardsec.com/index.html
● Add a visible, programmatically-associated <label> (or aria-label/aria-
labelledby) to every Contact form field.
● Mark required fields with both a visible indicator and the required/aria-
RECOMMENDATIONS
required attribute.
● Replace stat-value headings with short descriptive text (the stat value can
remain as content within the section).

8.3 Missing Autocomplete Attributes on Input Fields
STATUS CLOSED
WCAG 2.2 REFERENCE 1.3.5 Identify Input Purpose (Level AA)
